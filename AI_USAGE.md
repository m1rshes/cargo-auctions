# AI_USAGE.md

## Какие части делались с AI

Весь проект собирался при помощи AI (Claude) в парном режиме: от инициализации проекта (`create-vite`, установка стека) до реализации FSD-слоёв, MSW-моков, роутинга, форм и тестов. Это честный ответ — задание было выполнено как демонстрация работы с AI-инструментами, а не «AI написал 10%, остальное руками».

Конкретно AI:
- Спроектировал структуру FSD-слоёв и разложил сущности/фичи/виджеты по ней
- Написал типы по текстовому описанию OpenAPI-контракта из задания (в самом задании нет файла схемы — типы восстановлены по перечню полей и его смыслу)
- Реализовал MSW-хендлеры и мутируемый in-memory store (генератор аукционов/ставок, пересчёт ранга и текущей цены после `placeBet`)
- Реализовал TanStack Router (file-based routes, layout с вкладками, loader + `ensureQueryData`, типизированные search params)
- Реализовал форму ставки на RHF + Zod с динамической схемой на основе `min/max/step`
- Написал 25 unit-тестов на чистую логику
- Прогнал `tsc --noEmit`, `vite build`, `vitest run` — все проверки зелёные

## Какие решения кандидат принял сам

Поскольку весь код писал AI, «решения кандидата» здесь — это решения, принятые в диалоге по ходу разработки, а не после генерации кода:
- Выбор палитры и визуального языка (тёмная тема, teal/amber-акценты) вместо дефолтного AI-шаблона — сознательный уход от «cream + terracotta»
- Решение синхронизировать фильтры с URL search params (а не с localStorage), так как список аукционов — это адресуемое состояние, которым логично делиться ссылкой
- Решение вынести сворачивание панели фильтров в отдельный Zustand-store, а не в URL — это чисто визуальный UI-state, не часть «состояния страницы»
- Решение делать `/auctions/:auctionUuid/bid` отдельным роутом (а не модалкой) — по формулировке задания «режим установки ставки должен открываться по ссылке»

## Какие AI-предложения были отклонены

- Изначальный вариант мягкой проверки кратности цены шагу ставки (`step`) в MSW-хендлере был сознательно смягчён/отключён (оставлен как закомментированная заглушка) — в задании шаг ставки описан как подсказка UI, а не как жёсткое ограничение сервера, и жёсткая проверка кратности могла бы блокировать корректные с точки зрения пользователя ставки при округлениях
- Оставлен единственный источник состояния фильтров (URL), хотя задание допускает alternative «URL либо localStorage» — вариант с localStorage не реализовывался, чтобы не плодить два источника правды

## Какие места кандидат проверял особенно внимательно

- Соответствие полей `AuctionRestrictions` (`can_set_bet`, `hide_bets_history`, `hide_points_address_and_contacts`, `no_view_cargo_price`) их фактическому использованию в UI — на детальной странице, в списке и на вкладке ставок
- Пересчёт состояния после успешной ставки в MSW-store: отмена предыдущей ставки пользователя, пересчёт рангов активных ставок, обновление `trading.currentPrice`/`tradingStatus` и синхронного `listItem`
- Обработка 422 в форме ставки — что ошибки от сервера действительно привязываются к полю `price`, а не проглатываются
- Совпадение путей относительных импортов в файлах роутов (это единственное место, где сборка падала из-за неверной глубины `../`) — отдельно перепроверено после первой неудачной сборки
- Типизация `useForm` с `z.coerce.number()` — это единственное место, где `tsc` действительно ловил ошибку (несовпадение input/output типов формы), которая была устранена явными generic-параметрами `useForm<Input, Context, Output>`

## Какие риски остались

- **Нет визуальной проверки в браузере.** Среда разработки не имела доступа к headless-браузеру/скриншотам, поэтому вся проверка — это `tsc`, `vite build`, `vitest run` и построчный код-ревью. Возможны visual-баги (переносы текста, оверфлоу таблицы ставок на узких экранах), которые не всплывут в консоли сборки
- Часть API-контракта (типы, названия полей вроде `cargo_num` vs `cargoNum`) реконструирована по текстовому описанию задания, а не по реальной OpenAPI-схеме — при наличии официальной схемы возможны расхождения в именовании
- Отсутствуют компонентные/интеграционные тесты (React Testing Library подключена в devDependencies, но не использована) — покрыта только чистая логика
- MSW-стор не сохраняет состояние между перезагрузками страницы (in-memory) — это осознанный выбор для простоты, но нужно иметь в виду при демонстрации сценария «сделал ставку → обновил страницу»

## Что бы кандидат улучшил при наличии ещё одного дня

- Прогнал бы приложение в реальном браузере (Playwright/Chromium) и сделал бы визуальный QA-проход, особенно mobile-раскладки
- Добавил бы component-тесты на `AuctionBidForm` (RHF + Zod интеграция) и `AuctionsListWidget` (skeleton/empty/error через React Testing Library)
- Реализовал бы вариант персистентности фильтров в `localStorage` как fallback для случая, когда пользователь делится ссылкой без query-параметров
- Добавил бы retry/backoff и optimistic update для мутации ставки, чтобы UI обновлял `currentPrice` мгновенно, не дожидаясь инвалидации
- Провёл бы отдельную сверку с реальным OpenAPI-файлом, если бы он был приложен к заданию, вместо реконструкции типов по текстовому описанию
